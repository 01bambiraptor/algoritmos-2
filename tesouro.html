A ideia antes do código

      
Imagina uma fila de baús e você passando por eles um de cada vez, com uma moeda na mão: cara, o baú fica com o Leonardo; coroa, vai pro Enoque. Com 4 baús existem 2 × 2 × 2 × 2 = 16 jeitos de jogar as moedas. O solve testa esses jeitos em ordem, sempre primeiro o "não pega", e para assim que achar um em que o Enoque ficou com exatamente a metade.

      
É o mesmo desenho da aula de todos os subconjuntos: cada elemento entra ou não entra. A diferença é que aqui a gente não quer listar todos, quer saber se algum serve.


      
O que não está escrito mas existe

      

        1. Cadê o "desfaz"? No Resta Um e nas Rainhas tinha linha pra desfazer. Aqui não tem nenhuma. É porque soma é passada por valor: quando o código faz solve(meta, i+1, soma + objetos[i]), a conta vai pra uma variável nova, da chamada de baixo. A soma desta chamada nunca mudou. O desfazer acontece sozinho quando a chamada de baixo acaba.


        2. Quem é o Enoque no código? Só a soma. O código nunca calcula a parte do Leonardo. Ele não precisa: se o Enoque tem metade, o resto também é metade.


        3. A meta já vem dividida por 2. Quem calcula é o main: soma tudo, testa se é ímpar (se for, já imprime N sem chamar solve) e divide por 2.


        4. Por que i == n é a base? i é o baú da vez. Quando i chega em n, todos os baús já foram decididos. Só então dá pra conferir se soma == meta.
      


      
O jogo e o C são a mesma coisa

      

        
No jogoNo C

        
Botão "não pega"solve(meta, i+1, soma), a primeira chamada

        
Botão "pega"solve(meta, i+1, soma + objetos[i]), a segunda chamada

        
Terminou os baúsi == n

        
Desfazera chamada de baixo devolve 0 e acaba, e a soma volta a ser a desta chamada

        
"Não dá pra dividir!"a primeira chamada, solve(meta, 0, 0), devolve 0 e o main imprime N

        
A árvorecada nó é uma chamada, cada nível é um valor de i
